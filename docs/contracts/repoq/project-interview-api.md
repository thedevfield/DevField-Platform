# RepoQ — Project ↔ Interview API 계약 (간단 버전)

> **DevField — Practice. Solve. Grow.**  
> 문서 ID: `DF-API-RQ-001` | **v0.3 (수정 초안)** | 상태: **사용자 검토 완료 · GitHub 반영 전**  
> 기준: [RepoQ PRD v1.0](../../products/repoq/PRD.md) · [서비스 경계 설계서](../../architecture/repoq-service-boundaries.md) · [ADR-001](../../adr/0001-repoq-service-decomposition.md)

## 1. 무엇을 만드는가?

RepoQ에는 두 서비스가 있다.

- **Project Service:** GitHub 프로젝트를 등록하고 코드를 분석한다. 분석 결과를 저장하고 프로젝트를 삭제한다.
- **Interview Service:** 분석 결과로 자유 연습·모의면접을 진행하고, 질문·답변·평가·이력을 관리한다.

**두 서비스끼리 직접 주고받는 API는 우선 2개만 사용한다.** 웹 화면에서 Project에 보내는 **등록·재분석 요청**, Interview에 보내는 **면접 시작·답변 제출 요청**은 별도의 사용자용 API다. 이 문서에서 상세 경로를 정하지 않는다.

**Snapshot(스냅샷)** = 특정 GitHub Commit을 기준으로 저장해 둔 프로젝트 분석 결과. 재분석을 하면 기존 결과를 덮어쓰지 않고 새로운 결과를 만든다.

## 2. 사용자가 실제로 겪는 흐름

1. 사용자가 GitHub 저장소를 등록하면 Project가 분석한다.
2. 분석이 끝나면 사용자는 **자유 연습 / 모의면접** 중 하나를 선택한다.
3. 새 면접 시작 시 Interview가 Project에 **가장 최근에 사용 가능한 분석 결과**를 요청한다.
4. Interview는 받은 Snapshot을 해당 면접에 고정하고 질문·답변·평가를 진행한다.
5. GitHub 코드를 바꿨다면 사용자가 **재분석**을 요청한다. 재분석 성공 후 **새로 시작하는 면접부터** 새 Snapshot을 사용한다.

> 여기서 **최신**은 *GitHub에 올라온 실시간 최신 코드*가 아니라 **사용자가 마지막으로 분석에 성공해 면접에 사용할 수 있게 된 Snapshot**을 뜻한다. GitHub 변경만으로 자동 재분석하지 않는다.

## 3. 서비스 간 API — 딱 2개

| API | 호출 방향 | 목적 |
|---|---|---|
| `GET /internal/projects/{projectId}/interview-data` | Interview → Project | 새 면접을 시작할 때 사용할 분석 결과 받기 |
| `DELETE /internal/projects/{projectId}/interviews` | Project → Interview | 프로젝트 삭제 시 관련 면접 기록 전부 삭제하기 |

### ① 분석 결과 받기 — GET

Interview가 새 면접을 시작할 때 요청한다. Project는 **본인 프로젝트인지**, **삭제 중이 아닌지**, **면접에 사용할 수 있는 분석 완료본이 있는지** 확인한다.

**응답 예시:**

```json
{
  "snapshotId": "snap-02",
  "commitSha": "b2c3d4e5",
  "topics": ["API", "DATABASE"],
  "evidence": [
    { "path": "src/UserController.java", "summary": "회원 등록 API 구현" }
  ]
}
```

- `snapshotId`: 분석 결과 번호. Interview는 이 번호와 필요한 자료를 면접에 저장한다.
- `commitSha`: 분석에 사용한 GitHub 코드 버전(위 값은 축약 예시).
- `topics` / `evidence`: 실제 코드에서 확인한 질문 분야와 근거. **근거가 없는 기능은 질문하지 않는다.**
- 새 분석 결과는 코드 근거까지 모두 저장한 뒤 최신 완료본으로 지정한다. 한 응답에는 **같은 Snapshot의 자료만** 담고 서로 다른 버전의 코드를 섞지 않는다.

**재분석 시 어떤 결과를 쓰는가? (추천 정책)**

| 상황 | 새로 시작하는 면접 | 기존 면접 |
|---|---|---|
| 최초 분석 완료 전 | 시작 불가 | 해당 없음 |
| GitHub 코드만 수정, 재분석 안 함 | 기존 분석본 사용 | 기존 분석본 유지 |
| 재분석 진행 중 | 이전 READY 결과가 있으면 사용, 없으면 대기 | 기존 분석본 유지 |
| 재분석 성공, 새 READY 결과 생성 | **새 Snapshot 사용** | **기존 Snapshot 유지** |
| 재분석 실패·근거 부족 | 이전 READY 결과가 유효하면 사용 가능, 없으면 시작 불가 | 기존 분석본 유지 |
| 프로젝트 삭제 중 | 시작 불가 | 진행·기록 저장 차단 |

이전 분석본을 사용할 때는 화면에서 **“이전 분석 버전 사용 중”**임을 알린다. 재분석에 실패했다고 이전에 완료된 분석본이나 면접 기록을 지우지 않는다. 한 프로젝트의 재분석은 한 번에 하나만 진행해 결과 순서가 뒤집히지 않게 한다. 동일 Commit·동일 분석 결과라면 중복 Snapshot은 만들 필요가 없다.

**면접 시작 전 추가 확인:** 모의면접에서 근거 있는 주요 질문 5개를 만들기 어렵다면 시작하지 않는다. 근거 없는 질문을 억지로 생성하지 않는다. 자유 연습은 근거가 있는 분야만 선택할 수 있다.

**면접 도중:** Project를 매 질문마다 호출하지 않고, 시작할 때 확보한 Snapshot 자료를 사용한다. 일시 중단 후 재개하거나 AI 호출을 재시도해도 같은 Snapshot을 유지한다.

### ② 프로젝트의 면접 기록 삭제 — DELETE

사용자가 프로젝트 삭제를 요청하면 **Project가 순서를 관리**한다.

1. Project가 프로젝트를 **삭제 중** 상태로 바꾸고 새 분석·새 면접 시작뿐 아니라 **이미 진행 중인 분석의 늦은 저장**도 막는다.
2. Project가 Interview에 `DELETE`를 요청한다.
3. Interview가 **신규 면접·답변 저장·늦게 도착한 AI 평가 저장을 차단**하고, 해당 프로젝트의 질문·답변·평가·면접용 분석 자료를 삭제한다.
4. Interview가 전부 삭제했을 때만 `204 No Content`(삭제 완료)를 보낸다. 그러면 Project가 자신의 프로젝트·분석 데이터를 삭제한다.

**중간에 오류가 발생하면:** Project는 삭제 중 상태를 유지하고 같은 `DELETE` 요청을 다시 보낸다. 같은 요청이 반복돼도 문제없이 처리해야 한다(**멱등성** = 여러 번 요청해도 결과가 같음). 삭제 확인 전에는 사용자에게 완료라고 표시하지 않는다. 삭제 상태는 Project의 기존 사용자용 조회 기능에서 안내하며, 서비스 간 **별도 삭제 상태 조회 API는 만들지 않는다.**

**동시에 면접 요청이 들어오면:** Interview는 삭제 차단 상태를 저장해 두고, 실제 기록 저장 직전에도 확인한다. 삭제 요청이 시작되기 전에 분석 자료를 받아 간 면접이라도 **삭제 완료 후 새 기록을 만들 수 없어야 한다.** 삭제한 프로젝트 ID는 재사용하지 않는다. 같은 GitHub 저장소를 재등록하면 새 프로젝트 ID를 부여하고, **다른 사용자가 등록한 같은 저장소의 기록은 삭제하지 않는다.**

## 4. 오류와 보안 — 이것만 지키기

| 상황 | API 응답·동작 |
|---|---|
| 다른 사용자 프로젝트 또는 존재하지 않는 프로젝트 | `404` 등으로 접근 거부, 타인의 데이터 미노출 |
| 분석 완료본 없음 / 프로젝트 삭제 중 | `409` — 새 면접 시작 불가 |
| 서비스 장애·시간 초과 | `5xx` — 재시도 가능한 경우에만 안전하게 재시도 |
| 인증되지 않은 서비스 요청 | `401/403` — 요청 거부 |
| 면접 기록 삭제 완료(이미 삭제된 경우 포함) | `204` — 빈 응답으로 완료 표시 |

사용자 ID를 요청 본문에 적었다는 이유만으로 믿지 않는다. **로그인 사용자 권한**과 **두 서비스 사이의 호출 권한**을 서버에서 확인한다. GitHub 코드·README는 외부 입력으로 취급하고, 비밀정보가 분석 근거에 섞여 전달되지 않도록 한다. 구체적인 인증 제품은 추후 선택한다.

## 5. 이 문서에서 정하지 않는 것

- 웹 화면의 전체 API 경로 및 DB 테이블 구조, 인증·LLM·호스팅 제품.
- 분석 작업의 실제 수행 방식과 시간 제한, 재시도 횟수 등의 수치.
- 더 많은 내부 API, 메시지 브로커, 삭제 작업용 별도 API는 **실제 구현에서 필요해질 때만** 검토한다.

**기존 RepoQ 요구사항은 그대로 유지한다:** 자유 연습의 질문 묶음별 평가, 모의면접 주요 질문 **5개**·꼬리질문 **0~3개**·완료 후 평가 일괄 공개, 중단·재개·명시적 포기, 이력 보존과 사용자별 삭제 등. 이 문서는 서비스 간 연결만 간단히 정의한다.

> **상태:** 확정된 서비스 경계·PRD를 바탕으로 작성하고 사용자가 검토한 **간소화된 API 설계안**이다. 재분석 실패 시 이전 Snapshot 사용 등 세부 정책은 실제 구현·테스트에서 검증한다.

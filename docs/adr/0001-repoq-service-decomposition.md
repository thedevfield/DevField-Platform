# ADR-001 — RepoQ를 Project Service와 Interview Service로 분리

> **DevField — Practice. Solve. Grow.**  
> 결정 ID: `ADR-001`  
> 결정일: `2026-10-17`  
> 상태: **Accepted — 상위 서비스 경계 결정**  
> 제품: `RepoQ`  
> 관련 문서: [RepoQ MVP PRD v1.0](../products/repoq/PRD.md) · [RepoQ 서비스 경계 설계서](../architecture/repoq-service-boundaries.md)

## 1. 결정 요약

RepoQ는 **두 개의 독립 마이크로서비스**로 구성한다.

1. **Project Service:** 공개 GitHub Repository 등록·분석, 기준 Commit `AnalysisSnapshot`, 코드/문서 근거와 질문 가능 분야, 프로젝트·분석 생명주기 소유.
2. **Interview Service:** 자유 연습·모의면접, 주요·꼬리질문, 묶음/회차 정성 평가, 답변·복습·세션 이력 생명주기 소유.

두 서비스는 **하나의 `thedevfield/RepoQ` GitHub Repository**에서 관리하지만, 서로 **독립 빌드·테스트·배포**한다. 각 서비스는 자기 데이터를 소유하며 다른 서비스 DB에 직접 접근하지 않는다. 기본 통신은 **명시적 REST API**이고, 면접은 시작 시점의 불변 Snapshot을 사용한다.

프로젝트 삭제는 **Project Service가 절차를 조정**하며, Interview Service의 신규 기록 차단·관련 데이터 삭제가 확인된 후 Project 소유 데이터를 최종 정리한다. DevField 계정·SocialIdentity는 공통 Identity 책임으로 두되 별도 Identity 마이크로서비스와 인증 솔루션 선택은 보류한다.

> **결정의 경계:** 본 ADR은 **논리적 서비스 분리와 독립 배포 원칙**을 확정한다. DB 제품·물리 DB 서버 개수, Backend/Web 기술 스택, API Gateway, LLM 모델, 호스팅 업체를 확정하지 않는다.

## 2. 배경과 문제

RepoQ MVP는 사용자의 **실제 GitHub 프로젝트**에서 근거를 추출하고, 그 결과를 바탕으로 자유 연습과 실전형 모의면접을 제공해야 한다. 두 작업은 실행 특성과 변경 책임이 다르다.

- **프로젝트 분석:** 외부 GitHub API 의존, 파일 크기·유형 제한, 비동기 성격의 수집·분석, 버전 관리와 불변 근거 유지.
- **기술면접:** 세션 상태·사용자 답변·실시간에 가까운 질문 응답, 평가 공개 게이트, 일시 중단·재개·이력 관리.
- **공통 조건:** 1인 개발, 단일 개발 에이전트(Codex 또는 Claude Code 중 미선정), 11월 말 MVP 목표(필요 시 12월로 연장), 공개 웹 프론트엔드 Vercel 배포.
- **미래 확장:** AlgoField·InfraField는 별도 독립 제품으로 공통 사용자 경험을 공유하지만 RepoQ 이용을 전제하지 않는다.

최소한의 MSA 학습·운영 가치와 출시 가능한 MVP의 개발 복잡성 사이에서 경계를 결정해야 했다.

## 3. 평가 기준 (Decision Drivers)

1. **비즈니스 책임** — GitHub 프로젝트 생명주기와 면접 세션 생명주기의 분리 가능성.
2. **데이터 소유권** — Snapshot·근거와 질문·답변·평가의 진실 원본을 독립적으로 관리할 수 있는지.
3. **실행·장애 특성** — GitHub 수집 지연·Rate Limit과 LLM 면접 상호작용의 장애를 얼마나 분리할 수 있는지.
4. **독립 배포 가치** — 한 도메인 변경 시 다른 도메인 전체를 재배포하지 않아도 되는지.
5. **변경·운영 비용** — 1인 개발의 계약·통합·배포·관측·삭제 처리 비용.
6. **제품·Repo 정책과의 적합성** — DevField 제품별 저장소 운영과 향후 독립 제품 확장에 일관적인지.

## 4. 검토한 대안

| 대안 | 형태 | 장점 | 한계 | 판정 |
|---|---|---|---|---|
| **A. 단일 RepoQ Backend** | Project + Interview를 하나의 애플리케이션·배포 단위로 구성 | 가장 간단한 개발·트랜잭션·배포, 서비스 간 호출 없음 | 분석 지연/실패와 면접 처리의 배포·자원·장애 경계가 결합, 서비스 독립 배포 학습 가치 감소 | 미채택 |
| **B. Project + Interview** | **RepoQ 저장소 내 두 독립 애플리케이션·배포 단위** | 비즈니스·데이터 책임이 분명하고 독립 배포·장애 격리 가능, 별도 AI 서비스 없이 시작 가능 | REST 계약·분산 삭제·통합 테스트·각 서비스 운영 부담 | **채택** |
| **C. 세분화된 다수 서비스** | Project, Interview, AI, Auth, Gateway 등을 초기부터 모두 독립 서비스화 | 세부 책임별 확장·배포 제어 가능 | 1인 MVP에 과도한 통신·배포·계약·시크릿·운영 비용, 아직 증명되지 않은 분리 이점 | 미채택 |

> 위 비교는 정성 판단이다. 측정하지 않은 성능 향상·비용 절감·확장성 수치를 근거로 사용하지 않는다. A안 역시 합리적인 대안이지만, 승인된 DevField MSA 방향과 두 도메인의 명확한 책임 차이를 고려해 B안을 선택했다.

## 5. 결정 내용과 불변 규칙

### 5.1 서비스 및 Repository

- `RepoQ`는 **제품 기준 단일 Repository**로 운영한다. 저장소가 하나라는 이유로 하나의 프로세스/DB 소유권으로 합치지 않는다.
- Project Service와 Interview Service는 자체 빌드/테스트/독립 배포 가능해야 한다.
- `DevField-Web`은 별도 Repository이며 Vercel로 배포한다. 별도 Gateway 또는 서버 측 BFF는 후속 설계 대상이다.

### 5.2 데이터 소유권

| 소유 영역 | 진실 원본 |
|---|---|
| DevField 공통 Identity | `DevFieldUser`, `SocialIdentity` |
| Project Service | `RegisteredProject`, `AnalysisSnapshot`, `EvidenceReference`, `AvailableTopic`, 분석·프로젝트 삭제 상태 |
| Interview Service | `PracticeSession`, `QuestionBundle`, `QuestionTurn`, `BundleEvaluation`, `SessionEvaluation`, 출제 이력 |

서로 다른 서비스의 DB에는 직접 접근하지 않는다. 초기에는 물리 DB 서버를 공유하더라도 **서비스별 스키마·접근 계정·마이그레이션 소유권**을 구분할 수 있다. 서비스 간 참조용 ID는 Cross-service FK가 아니라 **API 계약**을 통해 검증한다.

### 5.3 서비스 통신과 면접 시작

- **기본 통신:** 동기 REST API.
- Project에서 공개 저장소를 분석하여 실제 근거가 충분한 `READY AnalysisSnapshot`을 제공한 뒤 Interview가 시작 가능하다.
- Interview는 세션 생성 시 **인증된 사용자 소유권·프로젝트 활성 상태·READY Snapshot**을 Project API로 검증한다.
- 면접은 선택한 Snapshot ID·Commit SHA에 **고정**하며, 재분석이 완료되어도 기존 세션의 분석 근거를 변경하지 않는다.
- 면접 진행 시 Project API 매 턴 호출을 지양하고 필요한 범위의 근거를 제한된 세션 컨텍스트로 확보한다. Project 장애 시 신규 시작은 제한될 수 있으나 이미 시작된 세션을 가능한 범위에서 유지한다.

### 5.4 사용자 면접 정책 (기존 PRD 보존)

- **FREE:** 전체 랜덤 또는 근거 있는 분야 선택, 과거 출제 질문을 참고해 의미 중복 최소화, 묶음별 정성 평가 즉시 공개.
- **MOCK:** 주요 질문 **5개** + 각 꼬리질문 **0~3개**, 이전 세션 이력은 새 질문 생성 컨텍스트에 사용하지 않음. 5개 묶음 응시 후 묶음 평가 5건 및 종합 평가 1건 공개.
- 일시 중단은 재개 가능하다. 사용자의 **명시적 포기**로 중도 종료된 미완료 MOCK은 해당 회차를 삭제하며 결과를 제공하지 않는다.
- 기술적 정확성·논리성·설계 근거·합리적 대안을 중심으로 **정성 평가**한다. 수치 점수는 후속 기능이다.

### 5.5 프로젝트 삭제·장애 원칙

- **Project가 삭제 작업 ID와 `DELETING` 상태를 관리**하고 신규 분석·면접 시작을 제한한다.
- **Interview는 해당 프로젝트 관련 쓰기를 차단하고** 세션·답변·평가·컨텍스트를 멱등적으로 정리한다. 재시도 요청으로 다른 데이터가 삭제되지 않아야 한다.
- Interview의 삭제 완료 확인 이후 Project가 분석 Snapshot·근거·프로젝트를 정리하고 최종 완료로 표시한다. 처리 중 오류는 삭제 중 상태를 유지한다.
- 별도 Kafka/Saga 프레임워크 등은 이번 결정의 필수 기술이 아니다.
- **진행 중 세션과 삭제가 겹치는 경쟁 상태**, 명시적 포기와 네트워크 장애의 혼동, 질문 평가가 미완료 MOCK에서 조기 공개되는 문제를 계약·테스트로 방지한다.

## 6. 결과 및 트레이드오프

### 기대 효과

- Project 분석과 Interview 면접 진행의 **비즈니스 경계 및 변경 책임**이 분명해진다.
- 각 서비스의 빌드·배포와 문제 진단을 독립적으로 수행할 수 있다.
- GitHub API 장애나 재분석이 기존 Snapshot에 기반한 면접 전체의 변경을 강제하지 않는다.
- 프로젝트별 단일 Repository 운영으로 여러 서비스의 통합 작업·계약 변경을 한 PR에서 검토할 수 있다.

### 감수하는 비용과 완화 방법

| 감수하는 비용/위험 | 완화 원칙 |
|---|---|
| 면접 시작에 Project API 호출 의존 | 세션 시작 시 Snapshot 고정·근거 확보, 오류·타임아웃·유효성 검사 |
| 두 서비스 간 API 변경 충돌 | 계약 버전·호환성 테스트, 단계적 배포/롤백, 공통 계약 경로 관리 |
| 서비스 간 데이터 참조와 삭제의 복잡성 | Project 조정·Interview 멱등 차단/삭제·완료 확인·재시도 |
| 추가 실행 단위의 운영 비용 | 처음에는 서비스 2개만, 같은 물리 DB 서버·최소 관측성도 검토 가능 |
| 장애 격리의 한계 | 같은 DB/호스팅 자원이나 공유 LLM의 장애는 함께 영향을 줄 수 있음을 명시하고 후속 실측 |
| 1인 개발에 따른 일정 위험 | 질문 근거 기반 Vertical Slice 우선, 독립 배포/계약 검증은 필요한 강도로 적용 |

이 ADR은 두 서비스로 분리하면 **성능이 자동으로 향상된다거나 장애가 완전히 격리된다는 의미가 아니다**. 실제 이점은 통합·배포·실패 주입 테스트로 확인해야 한다.

## 7. 설계 및 구현 수용 기준

- [ ] Project/Interview가 각각 독립 프로세스로 실행되고 독립 빌드·테스트·배포될 수 있다.
- [ ] 등록 프로젝트와 근거 Snapshot은 Project가, 면접 세션과 정성 평가는 Interview가 소유한다.
- [ ] 서로 다른 서비스 DB에 대한 직접 조회/교차 FK가 없다.
- [ ] Interview 시작 시 프로젝트 소유권·삭제 상태·READY Snapshot이 검증된다.
- [ ] 재분석 후 새 면접은 새 Snapshot을 사용하고 과거 이력은 기존 SHA를 유지한다.
- [ ] FREE와 MOCK의 과거 이력 입력/평가 공개 정책이 구분된다.
- [ ] 프로젝트 삭제를 중복·동시 요청하거나 면접과 경쟁시켜도 정리 완료 이후 데이터가 다시 생기지 않는다.
- [ ] Project/Interview 장애·LLM 오류·재시도를 포함한 핵심 계약 테스트가 있다.
- [ ] Web Vercel Production의 핵심 사용자 E2E를 통과한다.

> 체크리스트는 **향후 구현 수용 기준**이며, 아직 달성된 상태가 아니다.

## 8. 이 ADR에서 미결정인 항목

| 항목 | 후속 결정 위치 |
|---|---|
| API URI·메서드·스키마·HTTP 오류·내부 인증·멱등 요청 계약 | RepoQ API Contract |
| 계정 연결·탈퇴 등 공통 Identity 구현과 별도 서비스 여부 | 인증/보안 설계 ADR |
| DBMS·스키마·실제 ERD·삭제 트랜잭션·인덱스 | 데이터 모델/DB ADR |
| Project 분석 비동기 작업 처리 방식과 근거 컨텍스트 저장 | AI 분석 및 처리 설계 |
| Web → API 진입, Gateway/BFF/CORS, 배포 도메인과 서비스 호스팅 | Web/배포 아키텍처 |
| 모델/프롬프트/루브릭·AI 비용 한도와 품질 임계치 | AI 품질 PoC/운영 기준 |

## 9. 재검토 조건

다음 사례가 실제로 확인되면 이 ADR을 **새 ADR로 대체(Supersede)** 하거나 변경 이력을 기록한다.

- 독립 서비스로 분리한 결과, 서비스 간 연동·배포 복잡성이 실질적인 이점보다 지나치게 커진 경우.
- Project ↔ Interview의 데이터 왕복·요청 빈도가 병목으로 측정된 경우.
- 새로운 제품 요구사항으로 도메인 책임 또는 배포 단위가 바뀐 경우.
- 프로젝트 삭제·인증·운영 정책 때문에 현 경계를 유지하기 어려운 근거가 확인된 경우.

단순 선호도 변화나 MSA 도입 자체가 추가 서비스 분리의 근거가 되어서는 안 된다.

---

**결정 상태:** RepoQ를 Project Service와 Interview Service로 분리한다는 상위 결정은 **Accepted**이다. 이 문서의 향후 구현 체크리스트·제품/버전·호스팅은 아직 완료 또는 확정되지 않았다.
